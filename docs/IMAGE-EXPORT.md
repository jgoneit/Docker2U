# 컨테이너 이미지 내보내기

컨테이너 공통 도구막대의 **이미지 내보내기**에서 현재 Engine의 실제 이미지를
비압축 `.tar` 파일로 저장한다. 실행 중이거나 중지된 컨테이너를 지원하며,
Compose 등록 여부와 관계없이 사용할 수 있다. 컨테이너는 계속 실행된다.

## 사용 흐름

1. 컨테이너를 선택하고 **이미지 내보내기**를 누른다.
2. Engine, 컨테이너, 표시 이미지 이름과 실제 이미지 ID를 확인한다.
3. **저장 위치 선택**으로 macOS 저장 창을 열고 새 `.tar` 경로를 선택한다.
4. 경로를 확인한 뒤 내보내기를 시작한다. 기존 파일은 덮어쓰지 않는다.
5. 진행 화면에서 기록한 용량, 경과 시간, 결과와 저장 경로를 확인한다.

진행 창을 닫아도 작업은 계속된다. 하단의 **최근 이미지 내보내기**에서 다시
열 수 있다. 작업 결과는 앱 실행 중 최대 10개를 보관하며 앱 재시작 후 복구하지
않는다. 전체 크기와 진행률은 추정하지 않는다.

## 저장되는 내용

Core는 컨테이너의 `.Image`를 조회하고 고정된 이미지 ID로
`docker image save -- <image-id>`를 실행한다. 화면의 `.Config.Image` 태그는
설명을 위한 값이며 저장 대상을 결정하지 않는다. 이후 같은 태그를 다운로드하거나
빌드해도 준비한 이미지가 다른 이미지로 바뀌지 않는다.

이미지의 레이어와 이미지 설정을 저장한다. 볼륨·bind 데이터, Compose 파일,
컨테이너 실행 이후 쓰기 계층의 변경은 포함하지 않는다. 실행 중 컨테이너 전체의
백업이나 데이터베이스 백업 기능이 아니다.

ID로 저장한 아카이브에는 원래 이미지 이름과 태그가 없을 수 있다. 앱은 태그
보존을 위한 Engine 변경이나 아카이브 편집을 수행하지 않는다. 필요하면 복원 후
사용자가 이름을 지정한다. 앱 내부 가져오기·태그 편집은 이번 범위에 없다.

저장한 아카이브는 Docker CLI에서 다음처럼 읽을 수 있다.

```sh
docker image load --input '/path/to/image.tar'
```

이 명령은 사용자가 실행하는 복원 예시이며, 내보내기 과정에서는 실행하지 않는다.
형식은 [Docker image save](https://docs.docker.com/reference/cli/docker/image/save/)를
따른다. ID 입력의 이름·태그 처리는
[Moby exporter](https://github.com/moby/moby/blob/v28.4.0/daemon/containerd/image_exporter.go)에
근거한다.

## 실행과 파일 경계

- 준비 토큰은 세션·Engine·전체 컨테이너 ID·실제 이미지 ID에 연결된다. 정상 목록
  갱신은 허용하지만 새 연결이나 같은 이름의 새 컨테이너로 대상을 대체하지 않는다.
- native 저장 창이 고른 경로는 Core가 보관한다. IPC는 임의 경로·이미지 ID·명령을
  입력받지 않는다. 자동 다운로드·빌드·태그 생성도 수행하지 않는다.
- 바이너리 stdout은 파일에 직접 기록한다. 아카이브를 로그나 IPC에 실어 보내지
  않으며, 텍스트 출력 제한 때문에 8 MiB 이후 데이터가 잘리지 않는다.
- 같은 디렉터리의 새 임시 파일에 기록하고, 명령 성공과 파일 동기화 후 덮어쓰기
  없는 원자적 방식으로 최종 파일을 확정한다. 저장 중 대상 이름의 파일이 생겨도
  그 파일을 덮어쓰지 않는다.
- 취소·실패 시 소유 임시 파일을 정리한다. 정리 실패 시 남은 경로를 표시한다.
  비정상 프로세스 종료나 전원 차단까지 임시 파일 정리를 보장하지 않는다.
- 내보내기는 한 번에 하나이며 30분으로 제한한다. 닫기와 취소는 구별하고,
  재연결·앱 종료 시 진행 작업을 취소한다. 성공한 파일을 늦은 취소 응답으로
  삭제하거나 실패로 바꾸지 않는다.
- 시작 응답을 잃으면 같은 `requestId`로 결과를 확인한다. 자동 재실행하지 않는다.

## 검증

단위·fake CLI·브라우저·Native fixture 검사와 실제 Engine 검증은 별도로 기록한다.
현재 후보의 수행 결과와 제한은 `IMAGE-EXPORT-AUDIT.md`를 참고한다.

실제 Engine 회귀는 명시적으로만 실행한다. 검사는 UUID ownership label이 붙은
자원만 만들고 정리하며, 기존 사용자 컨테이너와 이미지에는 변경 명령을 보내지
않는다. 위 구현에서 사용하는 immutable BusyBox digest를 먼저 로컬 Engine에
준비해야 한다.

```sh
DOCKER2U_REAL_IMAGE_EXPORT=1 node scripts/with-toolchain.mjs cargo test \
  --manifest-path src-tauri/Cargo.toml --lib --locked \
  real_image_export_round_trip_preserves_running_and_stopped_containers \
  -- --ignored --nocapture
```

검사는 프로덕션 Core의 준비·저장 위치 등록·시작·조회 경로를 사용한다. 실행·중지
컨테이너의 ID와 상태가 유지되는지 확인한 뒤, 검증용 컨테이너와 이미지만 제거하고
각 tar를 load하여 이미지 ID와 ownership label을 다시 확인한다. Rust 검사는
native 저장 창의 실제 조작을 대신하지 않는다.
